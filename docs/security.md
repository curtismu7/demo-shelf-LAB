# Security notes

The shelf is a tool that runs on your own machine.

- **Loopback only.** It listens on `127.0.0.1`. Any other address needs `SHELF_BIND` set on purpose. While loopback-bound it rejects requests whose `Host` header is not `localhost`, `127.0.0.1` or `[::1]` (DNS rebinding).
- **No accounts, no secrets, no tokens.** Nothing the shelf stores or serves is a credential. It never forwards a cookie, header or token to a demo and sends demos only an unauthenticated `GET`. The health contract forbids secrets in the reply, and the shelf keeps only known fields from it.
- **SSRF stance.** The shelf fetches only the registered `url` plus `healthPath` (and `/`). No endpoint takes a URL or host from a request. Registered hosts must be loopback unless listed: the two SE hosted copies (`mocks.example`, `mocks.example`) are built in, and `SHELF_ALLOWED_HOSTS` adds more. Redirects are followed by hand, at most 3, and only within the registered origin; a redirect elsewhere shows as Down. Replies are capped at 4 KB, each request has a 3 s timeout, at most 4 run at once, and results are cached for 10 s (Refresh at most every 2 s). Registry files are your own files and are trusted only as far as the validation above.
- **Start / Stop is always on, and always Docker.** Host-run it needs a loopback bind (a non-loopback `SHELF_BIND` turns it off). Each call must be same-origin, name a registered id, come from a loopback client, and find `docker context show` = `orbstack`. It then runs `docker compose -f <registered file> [-f overlay] up -d` or `down` with no shell, a 60 s timeout and a minimal environment, one at a time per demo, and returns redacted output. The allowlist is the registry: there is no way to run any other command.
- **The container has no Docker access.** The shelf in Docker runs as a non-root user, with a read-only filesystem, all capabilities dropped, `no-new-privileges`, no Docker socket and no mounts of your demo folders (only the shelf's own `.data`, read-only). It is published on `127.0.0.1` only (a test pins this); inside the container the Host check stays on and every start is same-origin. To start or stop a demo it calls the **start agent** (`npm run agent`) on your machine.
- **The start agent.** Listens on `127.0.0.1` only, takes a bearer token (random, kept in `.data/agent-token` with mode 600, passed to the container by `npm run docker`, never logged), checks the Host header (`127.0.0.1`, `localhost`, `[::1]` or `host.docker.internal` on the agent port), and runs only the same compose call as above for an id found in the host's own registry. The caller sends an id and `start` or `stop`; it cannot send a path, a command or a compose file. A web page cannot call it: the token is a header a page cannot set cross-origin. Anything that can read `.data/agent-token` (or the container's environment) can start and stop the registered demos, and nothing else.
- **How the container sees your demos.** It connects to `host.docker.internal` (fixed by `SHELF_PROBE_HOST`, never from a request) and sends each demo's registered loopback Host header, because the demos refuse any other. Only loopback `http` URLs are rewritten this way.
- **What the page shows.** Status, timings, the registered URL and compose path, and the start command. Nothing from the demo beyond the fields in the health contract.
