# Security notes

The shelf is a tool that runs on your own machine.

- **Loopback only.** It listens on `127.0.0.1`. Any other address needs `SHELF_BIND` set on purpose. While loopback-bound it rejects requests whose `Host` header is not `localhost`, `127.0.0.1` or `[::1]` (DNS rebinding).
- **No accounts, no secrets, no tokens.** Nothing the shelf stores or serves is a credential. It never forwards a cookie, header or token to a demo and sends demos only an unauthenticated `GET`. The health contract forbids secrets in the reply, and the shelf keeps only known fields from it.
- **SSRF stance.** The shelf fetches only the registered `url` plus `healthPath` (and `/`). No endpoint takes a URL or host from a request. Registered hosts must be loopback unless `SHELF_ALLOWED_HOSTS` lists them: no host is built in. Redirects are followed by hand, at most 3, and only within the registered origin; a redirect elsewhere shows as Down. Replies are capped at 4 KB, each request has a 3 s timeout, at most 4 run at once, and results are cached for 10 s (Refresh at most every 2 s). Registry files are your own files and are trusted only as far as the validation above.
- **Start / Stop is always on, and always Docker.** Host-run it needs a loopback bind (a non-loopback `SHELF_BIND` turns it off). Each call must be same-origin, name a registered id, come from a loopback client (host-run; in the container see the trust boundary below), and find `docker context show` = `orbstack`. It then runs `docker compose -f <registered file> [-f overlay] up -d` or `down` with no shell, a 60 s timeout and a minimal environment, one at a time per demo, and returns redacted output. The allowlist is the registry: there is no way to run any other command. Stop acts on one demo: `down` on that entry's compose file and nothing else. `down` stops a whole compose project, so an entry whose compose file is in the shelf's own folder, or in a folder that gives the same project name (Compose names a project after its folder), is refused with `is-the-shelf` for both start and stop, before any Docker command runs.
- **The container has no Docker access.** The shelf in Docker runs as a non-root user, with a read-only filesystem, all capabilities dropped, `no-new-privileges`, no Docker socket and no mounts of your demo folders (only the shelf's own `.data`, read-only). It is published on `127.0.0.1` only (a test pins this); inside the container the Host check stays on and every start is same-origin. To start or stop a demo it calls the **start agent** (`npm run agent`) on your machine.
- **The start agent.** Listens on `127.0.0.1` only, takes a bearer token (random, kept in `.data/agent-token` with mode 600, passed to the container by `npm run docker`, never logged), checks the Host header (`127.0.0.1`, `localhost`, `[::1]` or `host.docker.internal` on the agent port), and runs only the same compose call as above for an id found in the host's own registry. The one other thing it runs is `scripts/docker-up.mjs`, once, when `npm run agent` starts (the shelf's own `docker compose up -d --build`, then the browser opens): a fixed script with no input from any request, run with the agent's own environment, as if you had typed `npm run docker`. It is skipped under `CI`, with `SHELF_AUTOSTART=0` or with a custom `SHELF_DATA_DIR`, and stopping the agent cancels it. The caller sends an id and `start` or `stop`; it cannot send a path, a command or a compose file. A web page cannot call it: the token is a header a page cannot set cross-origin. Anything that can read `.data/agent-token` (or the container's environment) can start and stop the registered demos, and nothing else.
- **The install check (read-only).** `GET /v1/installs` on the start agent (same token, loopback and Host rules, no write route) answers for every registered demo that has a compose file: `{ compose: "present" | "missing", images: "built" | "missing" | "unknown" }` and nothing else (no path, no command output, no error text). Nothing in the request is used: the ids come from the host's registry, never from the caller, and never become a path. `compose` is a file-exists test on the registered compose file and overlays. `images` runs, with no shell, `docker context show` (anything but `orbstack` gives `unknown`), `docker compose -f <file> [-f <overlay>] config --images` and `docker image inspect <image...>`, each with an 8 s timeout, at most 2 demos at once, cached 30 s and dropped for a demo after Start or Stop on it. The image names come from the compose file's own text, so each must look like an image reference (no leading `-`, no spaces or shell characters, at most 24) or the answer is `unknown`. Any failure is `unknown`, never an error. In a container the shelf asks the agent in the background and serves its cached answer; `/api/shelf` never waits for it. Host-run, the same code runs inside the shelf. The entry that is the shelf's own compose project is never sent to Docker.
- **How the container sees your demos.** It connects to `host.docker.internal` (fixed by `SHELF_PROBE_HOST`, never from a request) and sends each demo's registered loopback Host header, because the demos refuse any other. Only loopback `http` URLs are rewritten this way.
- **What the page shows.** Status, timings, the registered URL and compose path, and the start command. Nothing from the demo beyond the fields in the health contract.
- **Trust boundary of the container.** Inside the container every request arrives from the Docker network, so the shelf cannot tell your browser from another process. The only protection of the shelf's own Start / Stop endpoint is that the port is published on `127.0.0.1` plus the Host and Origin checks, and those stop web pages, not programs: any program or container on this machine that can open `http://127.0.0.1:4400` (containers reach it as `host.docker.internal:4400`) can send a forged same-origin request and start or stop the registered demos. That is the same reach any process running as you already has on this machine (host-run the loopback check passes for every local process too). The token protects the agent from everything except the shelf. What it cannot do is run anything other than `docker compose up -d` or `down` for a registered demo.
- **Hostile or broken demos.** A demo that answers the shelf's probe with a nonsense HTTP status, a reset connection or a hung socket shows as Down; it cannot crash the shelf (the probe treats a status outside 200-599 as a failed probe, and a test pins it).
